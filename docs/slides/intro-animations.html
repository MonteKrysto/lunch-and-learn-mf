Takeaways: microfrontends are a team-scaling tool · a remote is files that run in the browser · singletons are where it bites · every consumer owns its resilience.

Questions?

Our product: a revenue-cycle console. Four teams — but one frontend codebase, where every team’s UI leans on the same shared core. Everyone edits everything; merge conflicts are the tell.

And one deploy queue for the whole frontend: a single broken build parks every team’s release. Code coupling and release coupling, stacked.

Split along ownership lines instead — these are the actual apps in the repo you’ll clone: uikit, claims (a full application, with its own API and data), and worklist. Each deploys alone. Workspaces in one repo or separate repos — the boundary is what matters.

But users don’t want four apps — they want one. Here’s the shell: the RCM Console, with three empty slots. The rest of this talk is filling them — without giving up a single independent deploy.

Module federation, act one: uikit exposes components — real modules, published over HTTP via mf-manifest.json. Nothing consumes them yet; publishing is unilateral.

The shell declares remotes: uikit@…/mf-manifest.json and imports <MetricCard/> like any module — except it arrives at runtime, from uikit’s deployment. First slot filled.

Same move at application scale: claims exposes one module, <ClaimsApp/> — router, data layer and all — and the shell mounts it under /claims with a single basename prop.

The worklist fills the last slot — and consumes uikit’s badges itself while the shell consumes it. Federation is a graph. And everyone runs ONE React: shared … singleton. That line is where production bugs live.

Every slot shows the version its team last deployed — the shell never pinned any of this at build time; it discovers versions from each manifest at page load.

The uikit team ships v3.1. The open page keeps running v3.0 — a deploy never yanks code out of a live session.

Next reload: v3.1 composes in. Claims and worklist didn’t move. Three teams, three release cadences, zero shell redeploys.

Federation moves UI only — data stays plain HTTP. The dashboard, the widget, and ClaimsApp itself all call the claims team’s API. Consuming a team’s data doesn’t require consuming its UI.

And the API is a normal running service — deployed, versioned, and scaled like any backend. Each slice publishes two contracts: the exposed module for UI, the endpoints for data.

Now the part everyone gets wrong: a deployed remote is not a running app. It’s a folder — manifest, remoteEntry, hashed chunks. The only place a remote runs is the browser.

So remotes don’t need servers at all: every team’s CI uploads its folder to one store behind a CDN, and the shell composes from there. A deploy is a file copy. (make store + make publish simulate exactly this.)

The honest failure mode: uikit’s files unreachable → the runtime’s boot-time manifest fetch fails → the whole product blanks. A remote is a runtime dependency, and this is the bill.

Two layers of defense, about thirty lines: an error boundary around every slot, and the errorLoadRemote runtime hook — stub manifest for dead hosts, placeholder component for dead modules.

Same outage, new day: uikit’s slot degrades to a placeholder; claims and the worklist keep working. Every consumer owns its own resilience — bonus step 7 in the repo.
