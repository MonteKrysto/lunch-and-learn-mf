Four things to remember: microfrontends solve a team problem, not a code problem. A deployed remote is just files — it only runs in the browser. The shared-singleton line is where production breaks. And every consumer owns its own resilience.

Questions?

Here’s where we start. Our product is a revenue-cycle console, and four teams build it — but all of their code lives in one frontend codebase, leaning on the same shared components, styles, and routing. Two teams routinely end up editing the same files, because nothing in this picture belongs to any one team.

It gets worse at release time, because there’s only one pipeline. Right now the denials team’s build is failing — so the claims team’s urgent fix and the dashboard team’s finished feature are stuck in line behind it. Nobody can ship until somebody else fixes their build. That is the real cost of a shared codebase.

So we split it up — and this is the actual repo you’ll clone. uikit is the design-system team. claims is a complete application that owns its own API and data. worklist is the smallest team possible: one widget. Each of them builds and ships on its own — and whether they live as workspaces in one repo or as separate repos entirely, the ownership boundary is what matters.

There’s just one problem left: our users don’t want three separate apps — they want one. So here’s the shell: the RCM Console. Right now it’s mostly empty — three slots waiting for the other teams’ work. The rest of this talk is about filling those slots without giving up a single independent deploy.

Module federation starts on the producer’s side. uikit exposes two of its components — they become real, importable modules, published over HTTP through a small file called mf-manifest.json. Notice that nothing is consuming them yet. Publishing is something a team does on its own; nobody needs to ask permission.

Now the consumer’s side. The shell adds one line of configuration — “the remote called uikit lives at this manifest URL” — and then imports <MetricCard/> exactly like any other component. The difference is invisible in the code but enormous in practice: the component arrives at runtime, straight from uikit’s own deployment. First slot filled.

The same trick works at a much bigger scale. The claims team exposes exactly one module — <ClaimsApp/>, their entire application, router and data-fetching included — and the shell mounts it under /claims. The only thing the two teams had to agree on is a single prop telling the app which path it lives at.

The worklist fills the last slot, and does something interesting on the way in: it consumes uikit’s badges itself, while the shell is consuming it. Host and remote aren’t identities — they’re roles, and an app can play both at once. One last thing holds all of this together: every app shares a single copy of React. Remember that config line — it’s the one that breaks production when it goes missing.

Look at the version tags. Every slot is running whatever its team most recently deployed — uikit’s v3.0, claims’ v1.2, the worklist’s v2.1. The shell never chose any of these versions at build time. It discovers them fresh, from each team’s manifest, every single time the page loads.

Now the uikit team ships version 3.1… and nothing dramatic happens. That’s the point. Pages that are already open keep running v3.0, because a deploy never reaches into someone’s live session and swaps the code out from under them.

The next time anyone loads the page, it picks up v3.1 automatically. Claims and the worklist didn’t change, didn’t rebuild, didn’t even notice. Three teams shipping on three separate schedules — and the shell itself was never redeployed.

One thing federation deliberately does not touch: data. The UI arrives through federation, but data still travels over ordinary HTTP. The dashboard, the worklist widget, and the claims app all call the claims team’s API the normal way — and you can consume a team’s data without ever consuming its UI.

And that API is just a regular backend service. It deploys, versions, and scales like every other service you already run. So each team really publishes two contracts: the module it exposes for its UI, and the endpoints it exposes for its data.

Now for the fact that surprises almost everyone: a deployed remote is not a running application. It’s a folder — a manifest, a remote-entry file, and some hashed chunks. There is no server process behind it. The only place a remote ever actually runs is in the user’s browser.

Once you see that, the whole picture gets simpler: every team’s CI just uploads its folder into one storage bucket behind a CDN, and the shell composes the app from there. Deploying becomes copying files. In the repo, make store and make publish simulate exactly this setup.

Now the honest part. If uikit’s files ever become unreachable, the shell’s very first manifest fetch fails at startup — and by default, that takes the entire product down with it. A remote is a runtime dependency, and this blank page is the bill for all that independence.

The fix is about thirty lines of code, in two layers. A React error boundary goes around every slot, so one crashing remote can’t take down the whole tree. And the federation runtime gives you a hook — errorLoadRemote — where you hand back a stub manifest for a dead host, or a placeholder component for a module that failed to load.

And here’s that same outage on a better day: uikit’s slot politely says it’s unavailable, while claims and the worklist carry on working. That’s the deal you actually want — independence when things go well, containment when they don’t. It’s all in the repo as bonus step 7.
