Takeaways: microfrontends are a team-scaling tool · a remote is files that run in the browser · singletons are where it bites · every consumer owns its resilience.

Questions?

Four teams, four business domains — claims, denials, billing, eligibility — one codebase. The boxes are the org chart; the architecture just doesn’t know it yet.

Coupling #1: the code — same files, crossed wires. Coupling #2: the release — one broken build and every team’s work waits in the same queue.

First fix: draw the walls. Each domain becomes its own slice — own package, own config, own owner. This is a turborepo workspace, and it’s exactly the repo you’ll clone.

But follow the right side: the slices still funnel into ONE build and ride ONE release train. The coupling moved from code to release — sharing by npm package behaves the same way.

Cut the last coupling: each slice builds AND deploys alone. Independently developed, independently deployed — that is the definition of microfrontends.

A failure now stays where it happened. One question remains — and it’s the whole second act: who composes four deployables back into one product?

The npm way to share: publish uikit, and every consumer bakes a copy in at build time.

uikit ships v2 → every consumer must rebuild and redeploy to pick it up. The upgrade tax scales with the number of consumers.

Module federation: apps stay deployed; the browser composes them at runtime. uikit ships v2 → the next reload has it. Nobody rebuilt. And “deployed” means static files on a CDN — a remote only ever runs in the browser.

Every remote arrives carrying React. shared: { react: { singleton: true } } negotiates one copy — and this line is where production bugs live.

One page, three remotes, three different versions. The host never pinned these at build — it discovers what each remote is serving when the page loads.

The uikit team ships v3.1. Pages already open keep running v3.0 — a deploy never yanks code out of a live session.

Next load composes the newest of each: uikit moves to v3.1, claims and worklist don’t budge. Three teams, three release cadences, zero host redeploys.

The flip side: an exposed module is a runtime contract. claims ships a breaking v2.0 and the host meets it in production — keep exposed surfaces small and stable (ClaimsApp takes one prop for a reason).

A domain team ships a vertical slice: a UI remote (static files) and the API behind it (a running service) — apps/claims and apps/claims/api — each deploying on its own pipeline. Slices that don’t need an API don’t carry one.

Federation composes the UI only; data stays plain HTTP. The dashboard, the worklist, and the claims app itself all call the claims team’s API — consuming a team’s data doesn’t require consuming its UI.

The API deploys like any backend service — its own container, no federation involved. Its contract is the REST contract, versioned the usual way. Two contracts per slice: the exposed module for UI, the endpoints for data.

Topology one — what the demo runs: every remote behind its own host. Team boundaries are visible in the network tab, but N hosts must stay reachable and every load is CORS.

Topology two — the artifact store: every team’s CI uploads its build into one bucket behind a CDN. A deploy becomes a file copy, and remote servers stop existing. (make store + make publish simulate this.)

Topology three — co-locate the files with the host’s own origin: no CORS, one thing to keep reachable — but other teams’ CI writes into your bucket. The invariant everywhere: the host binds to a stable manifest URL; the rest is infra taste.

The failure mode nobody demos: one unreachable remote and the host is gone — the runtime fetches every manifest at boot, and a failed remote can unmount the whole React tree.

Two layers of defense, about thirty lines: an error boundary around every slot a remote fills, and the runtime’s errorLoadRemote hook — stub manifest for dead hosts, placeholder component for dead modules.

Same outage, new day: the dead remote degrades to a placeholder in its slot; everything else keeps working. Every consumer owns its own resilience — bonus step 7 in the repo.
